# C++ 代码注释规范（通用版）

> 目标：在任意 C++ 项目中可直接遵循的一套注释准则。
>
> 使用方式：第 1～3 节是必须遵守的原则；第 4～7 节是格式与内容约定；第 8～10 节是维护纪律；附录提供可直接复制的模板。团队落地时可只替换「术语表」和「示例」，无需改动规则本体。

---

## 1. 核心原则

1. **代码说明 What 与 How，注释说明 Why。** 读代码就能知道的事不写注释。
2. **先改善代码，再补注释。** 需要长篇注释才能看懂时，优先考虑重命名、拆函数、提取常量、引入类型。
3. **注释必须可信。** 过期注释比没有注释更有害，因为读者会把它当事实。
4. **注释描述当前实现，不描述设想。** 未实现的能力写进任务系统或设计文档。
5. **注释是接口契约的一部分。** 调用方只读注释就应当能正确使用接口，不必读实现。
6. **只写能严格成立的结论。** 性能、复杂度、线程安全等表述不得超出实际保证范围。

---

## 2. 注释的适用场景

### 2.1 必须写注释

| 场景 | 必须说明的信息 |
|---|---|
| 对外头文件、公开类、公开接口 | 职责、使用方式、契约 |
| 非平凡的算法与状态机 | 设计思路、阶段划分、不变式 |
| 所有权与生命周期 | 谁创建、谁释放、有效期、是否可为空 |
| 并发、锁、线程亲和性 | 在哪个线程执行、是否持锁、为何安全 |
| 副作用 | 修改了哪些外部状态、是否有 I/O、是否阻塞、是否抛异常 |
| 边界条件 | 空输入、溢出、越界、上限、单位、取值范围 |
| 有意为之的反直觉写法 | 不这样做会怎样，避免后人「修正」成缺陷 |
| 平台相关或非标准 API | 来源、可移植性、替代方案 |
| 精度、性能、资源消耗的取舍 | 为什么这样选、代价是什么 |

### 2.2 建议写注释

- 私有但逻辑复杂的函数。
- 非显而易见的常量取值与阈值。
- 复杂的模板约束与类型推导意图。
- 需要读者具备领域知识才能理解的公式或协议字段。

### 2.3 不需要写注释

- 自解释的访问器、简单构造/析构、明显的赋值与返回。
- 与相邻代码完全同模式、且已被说明过的重复结构。
- 命名已经准确表达语义的局部变量与短函数。

### 2.4 禁止出现

- 复述代码：`i++; // i 自增`。
- 无信息注释：`// 处理数据`、`// 重要逻辑`。
- 大段被注释掉的废弃代码。
- 作者签名、日期、修改流水账。
- 情绪化或口语化表述。
- 绝对化承诺：`// 无锁`、`// 零开销`、`// 线程安全`（若无依据）。
- 把规划写成事实：`// 支持 XXX`（实际未实现）。

## 3. 注释应说明的信息分类

写注释前，先判断这段代码缺失的是下面哪一类信息，只补这一类，不要全写。

| 类别 | 回答的问题 | 示例表述 |
|---|---|---|
| 意图 | 为什么需要这段代码 | 「为避免每次读取都搬移残留数据，改用游标记录消费位置」 |
| 契约 | 调用方必须遵守什么 | 「传入缓冲区必须至少包含 len 字节」 |
| 前置条件 | 调用前必须满足什么 | 「必须在 Stop() 之后调用」 |
| 后置条件 | 返回后保证什么 | 「返回时缓冲区已被清空」 |
| 副作用 | 会改变什么外部状态 | 「会写入文件并刷新内核缓冲」 |
| 边界条件 | 极端输入下行为如何 | 「len 为 0 时直接返回，不视为错误」 |
| 错误与异常 | 失败如何表现 | 「失败返回 false，不抛异常；内部状态保持不变」 |
| 所有权 | 谁负责释放 | 「返回堆对象，所有权移交调用方」 |
| 生命周期 | 有效期到什么时候 | 「指针仅在本函数同步执行期间有效」 |
| 线程与重入 | 能否并发调用 | 「非线程安全，只能由事件循环线程调用」 |
| 锁的边界 | 哪些操作在锁内 | 「锁内仅交换容器，I/O 在锁外完成」 |
| 复杂度与性能 | 代价按什么计 | 「推进游标为 O(1)；压缩为 O(剩余字节数)」 |
| 单位与取值 | 数值的含义 | 「超时时间，单位毫秒；0 表示不超时」 |
| 可移植性 | 是否平台相关 | 「glibc 扩展，非 POSIX 标准」 |
| 安全与健壮性 | 对不可信输入的处理 | 「长度来自对端，必须先校验上限再分配内存」 |

## 4. 注释形式与格式约定

### 4.1 三种形式的分工

| 形式 | 用途 |
|---|---|
| `/** ... */` | 声明前的文档注释：文件、类、函数、成员组 |
| `//` | 实现内部的解释、步骤、原因 |
| `///<` 或 `/**< ... */` | 成员变量、枚举值、常量的后置说明 |

### 4.2 文档注释标签

推荐使用 Doxygen 可识别标签，便于生成接口文档：

| 标签 | 用途 | 要求 |
|---|---|---|
| `@file` | 文件级说明 | 与 `@brief` 连用 |
| `@brief` | 一句话职责 | 不超过两行 |
| `@param` | 参数说明 | 每个参数一行，名称与签名一致 |
| `@return` | 返回值说明 | 非 void 必写，说明失败表现 |
| `@tparam` | 模板参数 | 写明类型要求或约束 |
| `@note` | 前置条件、有效期、线程约束 | 不重复 brief |
| `@warning` | 误用后果 | 明确后果，不写空泛提醒 |
| `@throws` / `@exception` | 抛出的异常 | 与实现一致 |
| `@see` | 相关接口或文档 | 使用相对路径或符号名 |
| `@deprecated` | 已废弃接口 | 必须给出替代方案 |
| `@name` + `///@{` `///@}` | 相关成员分组 | 仅用于真正成组的成员 |

### 4.3 排版细则

- 注释位于被说明代码的**上一行**，缩进与代码一致。
- 成员的后置注释与代码同行；同一段落内尽量对齐，代码过长时改放上一行。
- `//` 后空一格再写正文；块注释每行以 ` * ` 开头。
- 单行不超过团队约定行宽（建议 100 列），超出按语义换行。
- 长函数内可用分节横幅划分阶段，短函数不使用：

```cpp
// ==== 阶段一：解析输入 ====
// === 第 1 步：校验长度字段 ===
```

- 允许使用 ASCII 图说明复杂关系，但必须等宽对齐，并随代码同步更新。
- 不在注释中嵌入大段示例代码；确有必要时控制在 10 行以内。

### 4.4 语言与语气

- 团队内统一一种自然语言；技术术语、标识符、库名保留原文。
- 使用陈述句或祈使句，语气客观，不使用口语、反问、感叹。
- 术语在全项目保持一致，避免同一概念多种叫法（例如「会话」与「连接」不可混用）。
- 数值写清单位与取值含义；区间写清是否包含端点。

## 5. 文件级注释要求

### 5.1 何时需要

- 对外公开的头文件：**必须**。
- 实现文件：当模块职责不能从文件名直接看出，或包含重要设计约定时**必须**；否则可省略，避免重复头文件内容。

### 5.2 应包含的内容

1. 模块职责（一到两句）。
2. 关键设计约定：线程模型、所有权策略、错误处理策略、性能取向。
3. 使用上的重要限制或不支持的能力。
4. 必要时给出与其他模块的关系或阅读顺序。

### 5.3 不应包含的内容

- 版权声明与许可证之外的流水账。
- 逐个函数的清单（会迅速过期）。
- 与头文件完全重复的描述。

### 5.4 模板

见附录 A。

## 6. 函数级注释要求

### 6.1 公开接口必须包含

- `@brief`：一句话说明做什么，而非怎么做。
- 每个 `@param`：含义、单位、是否可为空、所有权是否转移。
- `@return`：取值含义、失败表现。
- 副作用：I/O、全局状态修改、阻塞、内存分配。
- 异常安全：是否抛异常、抛出哪些、失败时对象状态。
- 线程安全：可并发调用、需外部同步、仅限特定线程。
- 必要的 `@note` / `@warning`：前置条件、指针有效期、性能特征。

### 6.2 私有函数的简化规则

满足以下全部条件时，可只写一行 `//` 或不写：

- 函数名已准确表达语义；
- 参数与返回值类型自解释；
- 不涉及所有权转移、线程约束、非显然边界条件。

否则按公开接口标准写。

### 6.3 参数方向的表达

- 输入参数：说明是否被修改（一般不改，无需赘述）。
- 输出参数：必须标明「输出参数」，并说明失败时是否被改写。
- 输入输出参数：必须说明进入时的要求与返回时的状态。
- 指针与引用：必须说明是否允许为空、是否长期保存。

### 6.4 模板与重载

- 模板写 `@tparam` 说明类型要求，必要时给出可实例化的类型示例。
- 一组重载只在语义有差异时分别注释；完全同语义可在首处注释，其余用 `@see` 指向。

### 6.5 虚函数与接口

- 在**基类声明处**写完整契约，覆盖类不重复整段契约。
- 覆盖实现只写与基类不同的行为或额外约束。

## 7. 特殊标记

统一格式：

```cpp
// TODO(模块): 要做的具体事情，以及验收标准或触发条件
// FIXME(模块): 已确认的缺陷，影响范围与修复方向
// NOTE(模块): 读者必须知道的事实
// HACK(模块): 临时绕过方案，以及为什么暂时只能这样
// DEPRECATED: 已废弃，改用 XXX
```

规则：

1. **必须可执行**：写清做什么，不写「待优化」「以后看看」。
2. **必须有边界**：说明影响范围、触发条件或完成标准。
3. **必须能追溯**：大型项目建议关联 issue 编号。
4. **不得掩盖已知崩溃或数据损坏**：此类问题立即修复并排期，不用 FIXME 挂起。
5. **定期清理**：触及相关模块时检查一次；完成后立即删除标记。
6. **禁止用注释假装功能已实现**：未实现就保留 TODO。

## 8. 过时与冗余注释的处理

### 8.1 识别信号

- 注释提到的参数、返回值、函数名在代码中已不存在。
- 注释描述的流程与代码执行顺序不一致。
- 注释中的阈值、单位、线程模型与实现不符。
- 注释出现「暂时」「目前不支持」，而代码早已支持。
- 同一段信息在文件头、类注释、函数注释中重复出现且口径不同。

### 8.2 处理优先级

1. **代码错了就改代码**：注释描述的是正确设计时。
2. **注释错了就改注释**：实现是有意变更时。
3. **没有价值就删除**：只复述代码、无信息、已被命名取代。
4. **重复内容只保留一处**：以离契约最近的位置为准（通常是声明处），其余用 `@see` 指向。

### 8.3 删除原则

- 删除废弃代码时，连同其注释、分节横幅、ASCII 图一起删除。
- 不用注释保留旧实现，历史由版本控制保存。
- 删除前确认注释中没有仍有效的约束说明；有则迁移到保留位置。
- 过期注释按缺陷处理，不作为「风格问题」延后。

## 9. 注释与代码同步的维护规范

### 9.1 开发阶段

- 修改签名、语义、阈值、线程模型、所有权、复杂度结论时，**同一次提交内**更新注释。
- 重命名标识符时，全文检索注释与文档中的旧名称。
- 行为变更先更新注释再提交，不接受「下版再补」。

### 9.2 评审阶段

Reviewer 必须检查：

- 注释描述的行为能否在代码中逐条对应。
- 是否出现代码未实现却被写成已支持的能力。
- 是否存在代码已变而注释未变的区域。
- 新增公开接口是否具备完整契约说明。

### 9.3 重构与巡检

- 大规模重构后，对该模块的注释做一次专项校对。
- 定期（例如每个迭代）检查长期未变的「暂时」「目前」「暂不支持」表述。
- 文档、README、设计稿与代码注释对同一事实的口径必须一致；冲突时以代码为准并同步修订。

### 9.4 引用位置的写法

- 注释中引用其他代码，优先使用**符号名 + 文件路径**，避免写行号。
- 必须引用行号时，在文档头部注明基准版本或日期，并在后续变更中复核。

### 9.5 自动化建议（可选）

- 格式化交给 `clang-format`，注释规范只约束内容与结构。
- 静态检查可拦截：空的 `TODO`/`FIXME`、大段被注释掉的代码、与签名不一致的 `@param` 名称。
- 需要发布接口文档时，用 Doxygen 生成，并将「文档构建是否有警告」纳入 CI。

## 10. 正反示例对照

### 10.1 复述代码 vs 说明意图

```cpp
// 反例
offset_ += frame_size;  // offset_ 加上 frame_size

// 正例
// 仅推进读游标，避免每处理一帧都搬移缓冲区中的残留数据。
offset_ += frame_size;
```

### 10.2 模糊结论 vs 精确口径

```cpp
// 反例
// 解析是 O(1) 的

// 正例
// 推进游标为 O(1)；压缩仍需 O(剩余字节数)，代价按已消费字节数摊还，
// 不提供按消息条数的 O(1) 保证。
```

### 10.3 缺少约束 vs 写清生命周期

```cpp
// 反例
auto buf = std::make_shared<std::string>(std::move(payload));

// 正例
// 异步写返回时数据可能尚未发送完毕，且底层缓冲不拥有内存；
// 因此用 shared_ptr 持有，并由完成回调捕获，保证发送期间内存有效。
auto buf = std::make_shared<std::string>(std::move(payload));
```

### 10.4 无效接口注释 vs 完整契约

```cpp
// 反例
/** @brief 处理数据 @param data 数据 @param len 长度 */

// 正例
/**
 * @brief 将 data 中的 len 字节解析为一条完整消息
 * @param data 输入缓冲区首地址，必须至少包含 len 字节，不得为空
 * @param len  输入字节数；为 0 时直接返回 false
 * @return 解析成功返回 true；失败返回 false，且不修改内部状态
 * @note 不持有 data，调用方需保证其在函数返回前有效
 * @note 非线程安全，只能在事件循环线程中调用
 */
```

### 10.5 无信息注释 vs 有用的 Why

```cpp
// 反例
buffer_.resize(4096);  // 设置缓冲区大小

// 正例
buffer_.resize(4096);  // 单次读取的临时缓冲；数据随后追加到累积缓冲，因此可被下次读取覆盖
```

### 10.6 把规划写成事实 vs 如实描述

```cpp
// 反例
// 通过监听机制实现节点变化的实时感知

// 正例
// 当前仅监听会话建立事件；未注册节点变化监听，调用方需重新查询以获取最新状态。
```

### 10.7 含糊阈值 vs 带单位与后果

```cpp
// 反例
constexpr std::size_t kMaxHeaderSize = 64 * 1024;  // 最大头

// 正例
// 头部长度上限 64 KB；为 0 或超过该值判定为协议错误并关闭连接，
// 避免畸形长度导致连接长期等待无法凑齐的数据。
constexpr std::size_t kMaxHeaderSize = 64 * 1024;
```

## 11. 检查清单

作者提交前：

- [ ] 新增公开接口是否包含 brief、全部参数、返回值、副作用与线程安全说明？
- [ ] 指针与缓冲区是否写明所有者、有效期、是否可为空？
- [ ] 常量是否带单位，阈值是否说明越界后果？
- [ ] 性能与复杂度表述是否只声明能成立的部分？
- [ ] 是否残留复述代码、无信息注释、被注释掉的旧实现？
- [ ] 本次改动涉及的旧注释、图示、文档是否已同步？
- [ ] TODO/FIXME 是否可执行、有边界、可追溯？

Reviewer 评审时：

- [ ] 注释与实现是否逐条对应？
- [ ] 是否存在「已支持」但代码未实现的描述？
- [ ] 关键设计取舍是否只凭注释即可理解？
- [ ] 是否有应删除的重复或过期注释？

## 附录 A：可直接复制的模板

### A.1 文件级

```cpp
/**
 * @file xxx.cpp
 * @brief 模块职责一句话说明
 *
 * 关键设计约定：
 *  - 线程模型：由哪个线程调用，是否需要外部同步
 *  - 所有权策略：对象由谁创建与释放
 *  - 错误处理：返回值、异常或状态码的选择
 *
 * 使用限制：
 *  - 不支持的能力或不适用的场景
 */
```

### A.2 类

```cpp
/**
 * @brief 一句话说明该类职责
 *
 * 线程安全：是否可并发使用，若需外部同步请说明方式。
 * 所有权：持有的资源由谁释放。
 */
class Example {
public:
    // ...
private:
    int count_ = 0;             ///< 当前元素个数
    std::mutex mutex_;          ///< 保护 count_ 与内部容器
};
```

### A.3 公开函数

```cpp
/**
 * @brief 一句话说明功能
 * @param input 输入数据首地址，不得为空，所有权不转移
 * @param len   输入字节数，单位字节；为 0 时直接返回
 * @param output 输出参数，成功时写入结果；失败时不修改
 * @return 成功返回 true；失败返回 false 并可通过 Code() 查询原因
 * @note 会执行文件 I/O，可能阻塞；不要在实时线程中调用
 * @note 非线程安全，多线程调用需外部加锁
```
