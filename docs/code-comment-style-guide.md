# APRPC 代码注释规范

> 适用范围：`src/`、`example/` 下全部 C++ 源码与 `.proto` 文件；新增代码必须遵守，修改旧代码时同步整改所触及的注释。
>
> 制定依据：本规范提炼自仓库现有写法（`src/include/rpcprovider.h`、`src/include/logger.h`、`src/rpcprovider.cpp`、`src/logger.cpp`、`src/sequentiallogwriter.cpp`），目的是统一而不是推翻已有风格。
>
> 配套阅读：`docs/aprpc-project-review-and-interview-guide.md`（设计口径以代码为准，注释同样以此为准）。

---

## 1. 总则

1. **代码表达 What 和 How，注释表达 Why。** 凡是读代码本身就能知道的事，不写注释。
2. **注释是设计文档的一部分。** 一段好注释应让读者不必翻 git log、不必问作者，就能理解约束与取舍。
3. **注释的可信度高于一切。** 过期注释比没有注释更有害，因为它会被当成事实引用。
4. **注释描述当前实现，不描述规划。** 未实现的能力写进 `TODO` 或 `docs/` 设计文档，不写进函数注释。
5. **优先改代码，其次写注释。** 如果需要大段注释才能看懂，先考虑重命名、拆函数、提取常量。

---

## 2. 语言与术语约定

### 2.1 语言

- 统一使用**简体中文**书写注释，技术术语保留英文原文。
- 代码标识符（类名、函数名、变量、库名、API）一律原样书写，不翻译、不改写大小写。
- 句子使用完整中文标点（，。；：），但代码片段、路径、命令内保持英文标点。
- 一行注释尽量一句话说完；多句时使用编号列表，不堆砌长段。

### 2.2 术语统一表

| 统一写法 | 不要写成 |
|---|---|
| Boost.Asio / Asio | asio、boost asio、ASIO（句首除外） |
| Protobuf / protobuf | proto buf、PB |
| ZooKeeper / ZK | zookeeper（句中）、zk server |
| `io_context` | io context、IO上下文（可用「IO 上下文对象」作解释） |
| handler / 回调 | 句柄（与 handle 混淆） |
| 半包 / 粘包 | 拆包粘包混用时不加解释 |
| 帧（frame） | 包、消息（在同一段落里混用） |
| 读游标 `recv_offset_` | 偏移量、下标 |
| 前台缓冲 / 后台缓冲 | 前端后端缓冲与「前后端分离」混用 |
| 落盘 | 持久化（除非确实做了 `fsync`） |
| 临时节点 / 持久节点 | 短暂节点、永久节点 |
| 会话（session） | 连接（与 TCP 连接混淆时禁止） |

### 2.3 单位与数值

- 常量必须带单位：`64 * 1024` 注释写「64 KB」，`200ms` 写「200 ms」或「200ms」，全文统一。
- 区间写闭区间与含义：`header_size ∈ [1, 64 KB]`，不要只写「限制 64KB」。
- 线程数、缓冲区大小等**写清是硬编码还是配置项**，例如「8 个 worker 线程（当前硬编码，未读配置）」。

## 3. 注释类型、用途与适用范围

### 3.1 必须写注释的情况

| 对象 | 必须包含的内容 |
|---|---|
| 公开头文件 `.h` | 文件级或类级 `@brief`，说明该模块职责 |
| 类 / 结构体 | 一句话职责；有所有权或线程约束时必须写明 |
| 公开函数 / 对外接口 | `@brief`、每个 `@param`、`@return`（非 void）、必要的 `@note` |
| 非平凡私有函数 | 至少 `@brief`；涉及状态机、缓冲、并发时写完整注释 |
| 非平凡成员变量 | 行内说明其角色，尤其是指针、缓冲区、游标、锁 |
| 常量 / 阈值 | 含义 + 单位 + 为什么是这段范围（能写就写） |
| 枚举值 | 每个取值一行 `///<` 说明 |
| 并发、生命周期、所有权相关代码 | **强制**：说明谁持有、谁释放、在哪个线程执行、为何安全 |
| 复杂算法块（解帧、压缩、状态机） | 分节横幅 + 编号步骤 |
| 有意为之的「奇怪写法」 | 说明不这么做会怎样，避免后人「修正」成 bug |
| 平台相关 / 非标准 API | 注明来源与可移植性（如 `fwrite_unlocked` 是 glibc 扩展） |

### 3.2 可以不写注释的情况

- 自解释的 getters/setters、明显的一行构造函数。
- 与同一文件内已注释函数完全同模式的简单封装。
- 标准的 RAII 析构、明显的 `return`、循环计数器。

### 3.3 禁止写的注释

- 复述代码：`i++; // i 自增`、`lock.lock(); // 加锁`。
- 无信息注释：`// 处理数据`、`// 重要函数`、`// 临时方案`。
- 被注释掉的大段废弃代码（用 git 保存历史）。
- 情绪化或口语化内容：`// 这里很魔幻`、`// 别问我为什么`。
- 作者签名、日期、修改流水账（交给 git）。
- 绝对化性能承诺：`// 无锁`、`// 零拷贝`、`// O(1) 解析`（除非逐步论证且口径精确）。
- 把未实现能力写成已实现：`// 支持多路复用`（当前协议没有 `request_id`）。

## 4. 格式与排版

### 4.1 三种注释形式的分工

| 形式 | 用途 | 示例位置 |
|---|---|---|
| `/** ... */` | 声明前的文档注释（文件、类、函数、成员组） | `rpcprovider.h`、`logger.h` |
| `//` | 实现内的行内解释、步骤说明 | `rpcprovider.cpp`、`logger.cpp` |
| `///<` / `/**< ... */` | 成员变量、枚举值的后置说明 | `logger.h` 的 `LogLevel`、成员常量 |

```cpp
/// 声明前用块注释
class RpcProvider { ... };

enum LogLevel {
    INFO,       ///< 普通信息日志
    WARNING,    ///< 警告日志
    ERROR       ///< 错误日志
};

/// 成员常量后置说明
static constexpr std::size_t kSwapThreshold = 1024;    ///< active_buffer_ 积累多少条目触发后台线程唤醒
```

### 4.2 Doxygen 标签使用表

| 标签 | 何时使用 | 要求 |
|---|---|---|
| `@file` | 需要文件级说明的 `.cpp` | 与 `@brief` 连用 |
| `@brief` | 所有文档注释 | 一句话，不超过两行 |
| `@param` | 每个参数一行 | 名称与签名一致；说明含义与所有权 |
| `@return` | 非 void 函数 | 说明取值含义与失败表现 |
| `@note` | 前置条件、有效期、线程约束 | 补充约束，不重复 brief |
| `@warning` | 误用会出错的地方 | 明确后果 |
| `@tparam` | 模板参数 | 说明类型要求 |
| `@name` + `///@{` `///@}` | 一组相关成员 | 仅用于真正成组的成员 |
| `@see` | 指向相关实现或文档 | 写相对路径 |
| `@todo` | 见第 6 节 TODO 规范 | 必须可执行 |

### 4.3 排版细则

- 注释放在被说明代码的**上一行**，缩进与被说明代码一致。
- 成员行内注释在同行代码右侧，**同一段落内尽量对齐**；代码过长时改放到上一行。
- 单行注释 `//` 后空一格再写正文。
- 块注释每行以 ` * ` 开头，首行 `/**`、末行 ` */` 独立成行（与现有代码一致）。
- 一行不超过 100 列；超出就换行，换行后按语义对齐。
- 注释与上一段逻辑之间空一行，不与下一段代码之间空行。

### 4.4 分节横幅（长函数专用）

长函数内部用横幅划分阶段，与 `rpcprovider.cpp` 保持一致：

```cpp
    // ==================== 组织rpc请求的字符流 ====================
    // === 第一步：判断是否收到了完整的 4 字节 header_size ===
    // ==== 线程池 ====
```

- 阶段划分用 `// ==== xxx ====`，步骤用 `// === 第 N 步：xxx ===`。
- 横幅只在函数确实跨越多个阶段时使用，短函数不要加。

### 4.5 流程图与结构图

复杂交互允许在注释中放 ASCII 图，图前后各留一行空注释行，并保证等宽对齐：

```cpp
    /* 运行流程
     * 1. do_accept() 注册 async_accept
     * 2. 线程池中运行 io_context_.run()
     * 3. 回调中创建 Session 并再次调用 do_accept()
     */
```

图必须**随代码同步更新**；过期的图比没有图更误导。

## 5. 内容应包含什么

### 5.1 设计意图与取舍

```cpp
// 消费当前帧：只推进读游标，不搬移后续残留数据。
// 若改用 erase(0, frame_size)，粘包残留的 N 字节会被整段前移，产生 O(N) memmove。
```

### 5.2 前置条件与有效期

```cpp
 * @note args_data 只保证在本函数同步执行期间有效：protobuf 的 ParseFromArray
 *       会立即把数据反序列化进 message 对象，因此调用方无需再复制一份 args。
```

### 5.3 线程与锁的边界

必须写清三件事：**谁在调用、持不持锁、为什么安全**。

```cpp
// 无锁写入：只有 Logger 的后台单线程会调用本函数，FILE* 不存在多线程竞争，
// 因此可以使用 fwrite_unlocked，省掉 stdio 内部的 _IO_flockfile 开销。
```

```cpp
// 锁内只做容器交换；格式化、取时间、写文件全部在锁外进行，
// 生产者不会与磁盘 I/O 共持一把锁。
```

### 5.4 所有权与生命周期

```cpp
// 通过 shared_ptr 保持发送数据的生命周期，直到 async_write 完成回调执行。
// boost::asio::buffer 只是内存视图，不拥有数据。
```

### 5.5 复杂度与口径

- 只声明能严格成立的部分，必要时写出不能成立的部分。
- 涉及摊还、上限、阈值时，写明**按什么计**（按帧、按字节、按批次）。

```cpp
 * @note erase 本身是 O(remaining)，其代价至多按已消费字节数摊还，
 *       因此本函数不提供按帧数（尤其是变长消息）的 O(1) 保证。
```

### 5.6 单位、取值范围与默认值

```cpp
static constexpr std::size_t kMaxHeaderSize = 64 * 1024;  // header 长度上限 64 KB，越界视为协议错误并断连
static constexpr auto kFlushInterval = std::chrono::milliseconds(200); // 低流量时最长聚合窗口 200 ms
```

## 6. TODO / FIXME / NOTE / HACK 规范

统一格式：

```cpp
// TODO(模块): 要做的具体事情，触发条件或验收标准
// FIXME(模块): 已确认的缺陷，影响与修复方向
// NOTE(模块): 需要读者特别注意的事实
// HACK(模块): 临时绕过方案，以及为什么暂时只能这样
```

要求：

1. **必须可执行**：写清要做什么，不写「待优化」「后续看看」。
2. **必须有边界**：写清影响范围或触发条件。
3. **不得用于掩饰已知崩溃**：会崩溃的问题直接进 issue 并优先修复。
4. **不允许长期悬置**：每次相关模块改动时检查一次；已完成立即删除。
5. **不要在注释里写「已实现」来替代 TODO**：未实现就是未实现。

正例：

```cpp
// TODO(rpcchannel): 为 response_len 增加上限校验后再分配 vector，避免对端伪造长度导致一次性分配 4 GB。
// FIXME(zookeeper): Start() 将栈上 sem_t 的地址设为长期 watcher context，函数返回后可能悬空。
```

反例：

```cpp
// TODO: 优化一下
// FIXME: 这里有问题
// NOTE: 以后再说
```

## 7. 本项目专项要求

以下几类代码在本仓库中出错代价最高，注释必须覆盖。

### 7.1 异步回调

每个 `async_*` 调用处说明：

- 回调在哪个执行上下文运行（`io_context` worker 线程）；
- 捕获列表里每个对象为什么能活到回调执行；
- 缓冲区的内存由谁持有。

### 7.2 缓冲区与指针

- 指出缓冲区是**单次复用**还是**跨操作累积**（`buffer_` vs `recv_buffer_`）。
- 传裸指针 + 长度时，写明有效期与是否拷贝。

### 7.3 线程池与阻塞

- 说明 `Run()` 是否会阻塞、阻塞在哪、退出的前提条件。
- 说明业务逻辑是否与 I/O 共用线程。

### 7.4 协议与边界

- 帧格式、长度字段、字节序、上限，以代码中的常量为准。
- 明确区分「已实现的校验」与「仅有约定的上限」。

### 7.5 第三方语义

- `zookeeper_init` 非阻塞、`ZOO_EPHEMERAL` 绑定会话、`NewCallback` 返回堆对象需调用方释放等，都必须在调用点注释。

## 8. 注释与代码同步

1. **改代码必须同步改注释**，尤其是：参数列表、返回值语义、阈值、线程模型、所有权、复杂度结论。
2. **行为变了先改注释再提交**，不允许「代码已改、注释下版再补」。
3. **删除代码时删除对应注释**，包括上方的块注释、分节横幅和 ASCII 图。
4. **重命名标识符时全文检索注释中的旧名字**。
5. **注释中引用行号要慎用**：优先写函数名与文件路径；必须写行号时在文档头部注明基准日期。
6. **文档口径一致性**：代码注释、`README.md`、`AGENTS.md`、`docs/*.md` 对同一事实的说法必须一致；发现冲突以代码为准并同步修订。
7. Review 时把「注释是否与实现一致」作为与功能同级的检查项，过期注释按缺陷处理。

## 9. 正反示例对照

### 9.1 复述代码 vs 解释意图

反例：

```cpp
recv_offset_ += frame_size;  // recv_offset_ 加上 frame_size
```

正例：

```cpp
// 消费当前帧：只推进读游标，不搬移后续粘包残留数据；已消费前缀推迟到 CompactRecvBuffer 回收。
recv_offset_ += frame_size;
```

### 9.2 模糊结论 vs 精确口径

反例：

```cpp
// 解析是 O(1) 的
```

正例：

```cpp
// 推进读游标这一步是 O(1)；erase 仍是 O(remaining)，代价至多按已消费字节数摊还，
// 不提供按帧数的 O(1) 保证。
```

### 9.3 缺少约束 vs 写清线程与生命周期

反例：

```cpp
std::shared_ptr<std::string> write_buffer = std::make_shared<std::string>(std::move(response));
```

正例：

```cpp
// async_write 返回时数据可能尚未发完，而 asio::buffer 不拥有内存；
// 因此把响应移入 shared_ptr，并让完成回调捕获它，保证发送期间内存有效。
std::shared_ptr<std::string> write_buffer = std::make_shared<std::string>(std::move(response));
```

### 9.4 无效函数注释 vs 完整接口契约

反例：

```cpp
/**
 * @brief 处理请求
 * @param session 会话
 * @param args_data 数据
 */
```

正例：

```cpp
/**
 * @brief 根据服务名与方法名完成路由、反序列化并调用业务方法
 * @param session 会话对象，随回调持有以保证响应阶段会话仍存活
 * @param service_name 服务名称，用于在 serviceMap_ 中查找
 * @param method_name 方法名称，用于在 methodMap_ 中查找描述符
 * @param args_data 序列化后的参数首地址，直接指向接收缓冲区，不做拷贝
 * @param args_size 参数字节数
 * @note args_data 仅在本函数同步执行期间有效；业务方法不得在返回后继续访问 request
 */
```

### 9.5 无信息注释 vs 有用的 Why

反例：

```cpp
buffer_.resize(4096);  // 设置缓冲区大小
```

正例：

```cpp
buffer_.resize(4096);  // 单次读取的临时缓冲区；本段数据随后追加进 recv_buffer_，因此可被下次读取覆盖
```

### 9.6 把规划写成事实 vs 如实描述

反例：

```cpp
// 通过 Watcher 监听服务节点变化，实现服务动态上下线
```

正例：

```cpp
// 当前 Watcher 只处理会话连接成功事件，用于 sem_post 解除 Start() 的等待；
// 未对服务/方法节点注册 watcher，节点变化需要调用方重新查询。
```

### 9.7 含糊阈值 vs 带单位与后果

反例：

```cpp
constexpr std::size_t kMaxHeaderSize = 64 * 1024;  // 最大头
```

正例：

```cpp
// header 长度上限 64 KB；为 0 或超过该值视为协议错误，记录日志并关闭连接，
// 避免畸形长度让连接一直等待永远凑不齐的数据。
constexpr std::size_t kMaxHeaderSize = 64 * 1024;
```

## 10. 提交前自查清单

作者自查：

- [ ] 新增公开接口是否有 `@brief` + 全部 `@param` + `@return`？
- [ ] 指针、缓冲区、回调是否写明所有者与有效期？
- [ ] 并发代码是否写明执行线程与锁的边界？
- [ ] 常量是否带单位，阈值是否说明越界后果？
- [ ] 复杂度、性能表述是否只声明能严格成立的部分？
- [ ] 是否残留被注释掉的代码、签名、日期、无信息注释？
- [ ] 本次改动波及的旧注释、ASCII 图、文档是否已同步？
- [ ] TODO/FIXME 是否可执行、有边界？

Reviewer 检查：

- [ ] 注释描述的行为能否在代码中逐条对应？
- [ ] 是否出现「已实现」但代码中没有的能力？
- [ ] 是否存在代码已变而注释未变的情况？
- [ ] 关键设计取舍是否能只凭注释读懂？

## 11. 工具建议（可选）

- 注释统一使用 Doxygen 可识别格式，便于后续生成接口文档。
- 格式化交给 `clang-format`，不在注释规范中手工约束空格细节；本规范只约束注释内容与结构。
- CI 可增加简单检查：禁止 `// TODO$`、`// FIXME$` 这类无内容标记；禁止大段被注释掉的代码。
